# Second Brain · 后端答案引擎产品定义

## 问题是什么

F03 把结果页改成了"答案优先、证据其次、过程最后"的布局，但真实问答暴露出两个根本问题：

**后端收口不稳**：长任务跑完后，用户看到的是系统内部状态（"已到步骤上限"），而不是一个答案。这不是 UI 问题，是后端没有把执行失败转化为产品语义。

**默认证据是噪声**：引用区出现失败提交代码、样板定义、同一大文件的重复切片。知识库本身是混质的——题目笔记、方法论总结、提交记录、失败代码都混在一起——后端不做价值分层，前端怎么排版都救不了。

这两个问题决定了用户第一轮使用的信任感是否能建立。其他问题都排在后面。

---

## 要做什么

**一、让后端明确说出回答属于哪种情况**

每次回答必须落到三种状态之一：

- `full-hit`：问题的核心结论有直接证据支撑，没有明显缺口
- `partial-hit`：问题包含多个子问题或比较维度，至少一部分缺少足够证据
- `no-hit`：首轮检索没有命中高价值内容，直接收口，不扩大探索范围碰运气

这三种状态由后端判断并输出，前端直接消费，不猜测。

**二、让默认证据少而准**

默认主路径最多 4 条证据，优先选择：题目笔记、方法论总结、解释性段落。

以下内容默认不进主路径：失败提交、样板代码（如 `Definition for a binary tree node`）、同一大文件的重复切片、无解释价值的大表格。

Agent 推理过程中读到的内容可以用于内部判断，但不自动变成展示证据。

**三、失败时输出产品语义，不透传系统状态**

预算不足、命中为空、任务中断——这些情况后端应该输出"无记录"、"记录不足"、"系统繁忙，请稍后重试"，而不是"maximum steps reached"。

**四、citation 围绕命中片段组织，不推整篇大文档**

"定位原文"的默认视图应以命中片段为中心，展示足够判断真伪的小范围上下文。按需加载更多是二级能力，不是默认路径。

---

## 怎么判断做到了

| 验收项 | 标准 |
|--------|------|
| 首问完整收口率 | 高频真实问题集上，≥ 90% 的请求返回三种明确收口之一；系统内部状态透出率为 0 |
| 默认证据噪声率 | 噪声主证据占比 < 10%；同一大文件重复切片证据占比 < 20% |
| 边界判定一致率 | 在标注评测集上，三类收口的判定一致率 ≥ 90% |
| 核验成本 | citation 默认视图围绕命中片段，不默认加载整篇大文档 |
| 前端可消费性 | 后端输出能被前端直接映射为回答态、证据态、失败态，无需前端推断 |

---

## 不做什么

- 不把每一步工具调用和推理过程暴露给用户
- 不把"让 agent 探索更多"当成改进方向
- 不要求这轮解决所有长尾内容质量问题

---

## 拆分方向

1. 回答边界与收口契约（`full-hit / partial-hit / no-hit / failed` 的后端输出语义）
2. 默认证据质量与去重（展示证据准入规则，压制噪声切片）
3. 长任务阶段性回答与失败收口（预算紧张时仍优先输出可消费结果）
4. 低成本核验契约（citation 默认围绕命中片段，而非整篇大文档）
5. 后端评估与回归（围绕真实用户问题建立评测集）
