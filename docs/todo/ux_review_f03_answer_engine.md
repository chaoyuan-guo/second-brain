# F03 独立用户体验问题清单

> 用途：记录 `03_answer_engine_rearchitecture` 在真实产品路径上的独立用户体验问题，作为后续改进 TODO
> 检查时间：`2026-04-01`
> 检查环境：容器真源 `http://127.0.0.1:9080`
> 检查视口：桌面端 `1440 x 960`
> 检查方式：从独立用户视角实际提问、等待生成、切换会话、展开引用、打开原文预览、停止生成

## 1. 状态说明

`priority` 定义：

- `P0`：直接破坏主路径可用性或信任，用户很容易在首次使用时流失
- `P1`：主路径可走通，但结果质量或理解成本明显不达标
- `P2`：不至于阻断主路径，但会持续制造误操作或认知负担

`close` 定义：

- `no`：问题仍存在，未解决
- `yes`：问题已解决

当前这轮记录的所有问题状态均为 `close = no`。

## 3. 详细记录

### UX-F03-01 长任务阶段长期无正文，最终暴露系统内部失败文案

触发步骤：

1. 打开首页真源 `http://127.0.0.1:9080`
2. 点击推荐问题 `Quick Sort 和 Merge Sort 在什么场景下各自更优？`
3. 发送问题并等待

实际现象：

- 页面长时间只有过程摘要和状态文案
- 生成态中没有出现任何可消费的回答正文
- 最终主答案变成系统资源限制说明，而不是对问题的回答

预期行为：

- 只要已有可确认正文，就应该优先展示正文
- 如果最终失败，也应该是产品化失败收口，而不是系统内部限制透传

为什么是 `P0`：

- 这就是用户的第一次核心体验
- 用户不需要理解系统资源和步骤上限，只会得到一个结论：这个产品没有回答我的问题

### UX-F03-02 默认引用相关性和去重失真

触发步骤：

1. 发送排序算法问题并等待完成
2. 查看默认引用来源
3. 再发送 `我的笔记里有哪些关于平衡二叉树的内容？`
4. 查看第二次回答的默认引用来源

实际现象：

- 多条引用来自同一个大文件，来源多样性不足
- 默认路径出现 `Runtime Error`、`未通过提交代码`、样板定义类文本
- 引用标题与内容有时像是噪声片段，而不是支撑回答的关键依据

预期行为：

- 默认主路径里的引用应该服务于 先判断能不能信
- 证据应该少而准，而不是把能命中的片段尽量塞上来

为什么是 `P0`：

- F03 的核心目标之一就是让证据区帮助判断可信度
- 如果默认引用本身像噪声，整个结果页重构就会失去支撑

### UX-F03-03 回答正文截断

触发步骤：

1. 发送 `我的笔记里有哪些关于平衡二叉树的内容？`
2. 等待回答完成
3. 检查回答正文末尾

实际现象：

- 正文断在半句
- 列表结构未闭合
- 页面上没有告诉用户这是中断、停止，还是生成完成

预期行为：

- 回答要么完整收口，要么明确说明被截断的原因

为什么是 `P1`：

- 这不会让页面完全不可用
- 但它直接伤害结果质量，用户很难继续相信后续内容

### UX-F03-04 原文预览默认加载体量过大

触发步骤：

1. 在第一轮结果中展开第一条引用
2. 点击 `定位原文`

实际现象：

- 预览直接显示大范围原文
- 当前预览元信息为 `已加载 385219 / 590967 字符`
- 高亮虽存在，但用户要在大文档中重新建立上下文

预期行为：

- 默认以命中片段为中心展示小范围上下文
- 把 大文档按需展开 作为二级能力，而不是默认路径

为什么是 `P1`：

- 技术能力已存在
- 但产品效率不够，真实用户仍然很难快速做证据确认

### UX-F03-05 草稿跨会话悬挂，容易误发

触发步骤：

1. 创建第二个会话
2. 在第二个会话生成中输入追问草稿
3. 切回上一个会话

实际现象：

- 草稿在切换后仍保留
- 页面没有给出足够强的 当前草稿归属哪个会话 提示

预期行为：

- 草稿要么明确绑定当前会话
- 要么在跨会话保留时给出明确归属提示

为什么是 `P2`：

- 不是主路径阻断问题
- 但会在重度用户的多会话场景里持续制造误发和困惑

## 4. 建议的处理顺序

1. 先处理 `UX-F03-01` 和 `UX-F03-02`
2. 再处理 `UX-F03-03` 和 `UX-F03-04`
3. 最后处理 `UX-F03-05`

原因：

- 前两项直接决定产品首轮体验是否成立
- 中间两项决定答案和证据是否真的可用
- 最后一项更偏会话使用效率优化
