# 精准回溯原文产品判断

> 当前范围：只讨论“精准回溯原文”
> 关联执行：`docs/features/precise_traceability/rd_plan.md`
> 关联契约：`docs/features/precise_traceability/source_refs_contract.md`

---

## 1. 真正的问题是什么

用苏格拉底式提问继续往下追，这个需求当前真正的问题已经不是：

- 我们有没有 citation
- 我们能不能跳到原文
- 我们还要不要继续加更多透明度功能

真正的问题是：

**用户点开 citation 之后，能不能立刻确认这就是支撑刚才那句话的原文。**

如果答案还是“还得自己再读、再找、再判断”，那这个需求就还没有真正完成。  
从用户产品角度看，“能跳到附近”只是中间能力，不是最终价值。最终价值是：

**把局部断言变成可秒级验证的记忆入口。**

---

## 2. 事实与约束是什么

用第一性原理看，这个问题可以还原成几条事实和约束。

### 已经成立的事实

- native 主链路已经成立，正文关键断言能带 `[cxx]`
- `source_refs` 已能稳定提供 `path + citation_id + snippet + char_offset`
- 命中类问题已经不再主要依赖 synthetic / file fallback
- 单题、串行、并发 smoke 都已经证明这条链路不是偶发 demo

### 当前仍然存在的约束

- 用户的注意力是稀缺资源，不能要求他点击后再自己二次搜索
- 只要 `snippet` 里还混有包装噪音，证据确认成本就会升高
- 只要落点还偏宽，citation 就更像“相关材料”，而不是“断言依据”
- 不能为了改善体验，把主链路退回前端补偿或 synthetic 拼装

### 由此得到的结论

这个问题当前的瓶颈，不在组件层，不在更多 UI，不在更多解释文本，而在：

**原生证据片段的产品质量。**

---

## 3. 下一步唯一最该做的事

用奥卡姆式简化之后，下一阶段只做一件事：

**把 citation 打开后的证据片段，打磨成“可秒级确认”的体验。**

这件事可以展开成三条最小要求：

1. `snippet` 更干净  
   默认接近原始笔记内容，去掉 `Assistant`、heading、读取包装等噪音。

2. 落点更聚焦  
   点击后默认看到的应该是支撑当前断言的那一小段，而不是“附近差不多在这”的宽泛区域。

3. 对应关系更直接  
   用户不应读完整段后才猜出证据点，打开后就应能看懂“为什么这段话支撑刚才那句回答”。

---

## 4. 为什么不是做别的

按现有公理，这一步优先级高于其他相关改动：

- 按 T01，当前瓶颈在证据片段质量这层基础设施，不在更多前端组件
- 按 T02，重点不是继续约束过程，而是把“2 秒内确认依据”这个结果稳定做出来
- 按 V02，精准回溯原文本质上是可验证性需求，不是展示性需求
- 按 A12，应优先提升原生 `source_refs` 的证据质量，而不是上应用层补偿
- 按 M05，先收掉不必要复杂性，避免同时推进多个透明度方向而分散注意力

所以当前阶段先不做：

- 过程语义化摘要
- 更大的 AnswerPanel 重构
- 新的透明度组件扩展
- 为个别题目单独打补丁的过拟合优化

---

## 5. 当前完成度

从产品角度看，当前完成度大约是 `80%-85%`。

已经完成的是：

- 用户可以顺着回答回到自己的原文
- citation 已经从“像引用”变成“真能回查”

还没完全完成的是：

- 回到原文后，用户能否几乎不费力地确认这就是依据

所以这项能力已经具备交付价值，但还没有完成最后的产品化收口。

---

## 6. 下一阶段只看什么

下一阶段只看这 4 条：

1. A01、A03、A04、A05 这类命中题中，正文 citation 继续稳定走 `precise/native`
2. 点击 citation 后，默认看到的 `snippet` 不包含明显系统包装噪音
3. 用户能在 2 秒内判断“这就是支撑刚才那句话的证据”
4. 为了做到上面 3 条，没有把主链路退回前端 fallback 或 synthetic 补偿

这 4 条稳定成立，就可以认为“精准回溯原文”这个需求基本收口。

---

## 7. 一句话结论

“精准回溯原文”接下来最重要的，不是再证明系统能跳到原文，而是把跳过去之后看到的那一小段内容，做成真正一眼可确认的证据。
