# 证据可追溯性与过程透明度研发计划

> 用途：执行文档
> 关联：`docs/features/evidence-and-transparency-redesign.md`
> 契约：`docs/features/evidence-and-transparency-source-refs-contract.md`
> 验收：`docs/features/evidence-and-transparency-smoke-checklist.md`

---

## 1. 当前判断

这项需求已经进入“可用但未稳定验收”的阶段。

已经具备：

- 回答中的 `[cxx]` citation 渲染与点击交互
- 引用来源面板与原文预览
- 基于 `snippet + char_offset` 的附近定位与高亮
- synthetic source ref 与文件级来源兜底
- 可追溯性评估指标与部分单测

还没收口：

- 原生 `source_refs` 在常见命中类问答中的稳定性还没有被明确验证
- 精准片段级引用和文件级兜底引用还没有完全拉开语义边界
- 还没有一组固定样本来判断“这次是真的达标了，还是只是 demo 可用”

---

## 2. 本轮目标

本轮只做 4 件事：

1. 让有直接证据的回答，核心事实句旁稳定出现可点击 citation
2. 让用户点击 citation 后，能直接看到支撑片段，并立即知道它为什么支撑当前回答
3. 让精准片段级引用与文件级兜底引用在前端表达上明确区分，不制造虚假精确感
4. 建立一组固定样本，作为后续迭代的最小验收闭环

非目标：

- 不追求这一轮升级成严格行号级定位
- 不重做整套评估体系
- 不继续扩展更多展示组件

---

## 3. 实施策略

原则只有两条：

1. 优先把精准回溯建立在 OpenCode 原生 `source_refs` 上
2. 前端补偿只用于避免体验断裂，不升级成默认主路径

执行约束：

- 如果高频命中问题长期拿不到稳定 `source_refs`，应明确标记为上游 blocker
- 进入下一步之前，必须先有可观察结果，而不是“方向基本正确”

---

## 4. 当前任务看板

依赖关系说明：

- `source_refs` 最小字段契约说明可以与稳定性盘点并行推进
- 主关键路径是：确认原生 `source_refs` 稳定性 -> 收紧前端语义边界 -> 补齐前端回归测试 -> 增加人工走查清单
- 人工走查清单适合放在主要行为收口后整理，不建议前置

| 状态 | 任务 | 下一步 | 完成标志 |
|---|---|---|---|
| 可并行 | 补一份 `source_refs` 最小字段契约说明 | 基于现有事件与前端依赖字段整理 | 团队对原生证据链路的最低要求形成书面共识 |
| 进行中 | 确认原生 `source_refs` 在常见命中类问答中的稳定性 | 先跑最小样本并记录字段覆盖情况 | 能明确回答哪些问题已稳定返回 `path / citation_id / snippet / char_offset`，哪些还不行 |
| 待做 | 运行固定样本并产出首版基线结果 | 按 A01-A06 执行一次并记录结果 | 已有一版可复查的样本结果，可用于后续回归对比 |
| 待做 | 收紧“精准片段级引用”和“文件级兜底引用”的前端语义边界 | 基于稳定性盘点结果，列出当前会误导用户的具体场景并逐项收口 | 前端不再把文件级来源误读成精准片段证据 |
| 待做 | 补齐引用定位与降级语义的前端回归测试 | 先覆盖单文件命中、多来源命中、no-hit | 关键样本的交互与降级场景有回归保护 |
| 收尾 | 增加人工走查清单 | 结合固定样本整理成容器环境下的走查步骤 | 可以用同一套清单重复验收 |

风险与阻塞：

- 上游若不能稳定返回 `citation_id + snippet + char_offset`，精准回溯会停留在“部分可用”
- 如果继续把 file-level fallback 也算作“引用成功”，会导致项目误判已完成
- snippet 清洗、截断、格式归一化可能导致点击后只能落到宽泛区域

---

## 5. 阶段验收口径

满足以下条件，才算这一轮基本完成：

1. 常见命中类问答中，核心事实句能稳定出现可点击 citation
2. 在固定样本 A01-A06 中，命中类问题的 citation 主路径以原生 `source_refs` 为主，而不是前端 synthetic 补偿
3. 用户点击 citation 后，默认能直接看到支撑片段，并能立即识别其与当前回答的关系
4. file-level fallback 被清晰视为降级路径，而不是精准回溯达标表现
5. 固定样本 A01-A06 已有首版基线结果，后续改动可以用同一套样本复跑对比

---

## 6. 固定样本

这组样本只保留最关键的 6 个，够用即可。

| ID | 问题 | 用途 | 通过标准 |
|---|---|---|---|
| A01 | 回溯算法中 `path.pop()` 的作用是什么？笔记里是怎么解释的？ | 单文件精准回溯 | 回答有 citation；点击后直接看到“机器人退回”那段解释附近 |
| A02 | 回溯函数的入参设计我一直搞不清楚，笔记里有讨论过吗？ | 用户困惑回溯 | 回答引用用户自己的困惑与解释，而不是退化成通用教程 |
| A03 | BFS 的两种计步方式有什么区别？我在哪道题里搞混过？ | 多来源拼接 | 能稳定引用两个来源；点击不同 citation 能看到不同文件片段 |
| A04 | 我 2026-01-13 提交的最长回文子序列代码（提交 690994503）有什么 bug？ | 提交记录诊断 | 回答引用具体提交；点击后能定位到对应提交附近内容 |
| A05 | 2026-01-06 我在零钱兑换上连错两次，分别是什么问题？ | 诚实纠偏 | 必须先纠正“实际不止两次”，再给出可追溯分析 |
| A06 | 我笔记里系统写过树状数组吗？ | no-hit 诚实性 | 明确回答没有相关记录；不生成伪 citation，不误命中无关来源 |

建议用法：

- 工程链路先看 A01、A03、A04、A06
- 前端语义重点看 A01、A03、A06
- 诚实性重点看 A05、A06

执行记录时，最少记这几项：

- 是否有 inline citation
- 是否有可用 `source_refs`
- 是否有 `path / citation_id / snippet / char_offset`
- 点击后是否能直接看到支撑片段
- 是否出现伪 citation、错链或宽泛落点

## 7. 维护方式

这份文档只做一件事：帮助团队快速推进和快速验收。

后续维护原则：

- 只在任务状态、验收口径、样本列表发生变化时更新
- 新失败模式出现时，优先替换样本，不轻易扩表
- 如果文档再次变长，优先删背景说明，保留任务、验收、样本
