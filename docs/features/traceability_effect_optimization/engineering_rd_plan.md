## 1. 当前判断

“精准溯源”主链路已经完成。当前研发任务不再是打通 `precise/native`，而是提升其证据片段质量，使点击后的首屏体验满足“可秒级确认”的产品要求。

当前约束如下：

- 主链路必须继续保持 `precise/native`
- 不得通过前端 fallback、正文反推或 synthetic/source path 冒充 native precise
- 本阶段聚焦命中类样本 A01、A03、A04、A05
- 验收重点从“链路是否存在”转为“证据片段是否足够干净、聚焦、易确认”

结合当前实现，问题实际分布在 3 个层次：

1. 原生证据生成层  
   `docker/opencode-config/plugins/native-evidence-read.js` 负责生成 `source_refs.snippet` 与 `char_offset`。

2. 事件适配与引用标准化层  
   `frontend/src/app/api/_lib/event-adapter.ts` 与 `frontend/src/app/lib/citation-utils.ts` 已经承担了一部分 `snippet` 清洗与引用归并。

3. 预览展示层  
   `frontend/src/app/page.tsx` 基于 `char_offset + snippet` 决定加载窗口、定位方式与高亮范围。

因此，本阶段不是单点修复，而是**先分层定位问题属于哪一层，再把修复落在最低且最通用的有效层级**。

---

## 2. 本阶段目标

本阶段只做 1 件事：

**提升 citation 打开后的证据片段质量，使首屏内容更接近真实依据，而不是读取结果包装。**

将该目标拆为 3 项实施结果：

1. `snippet` 去噪  
   减少 `Assistant`、`User`、XML/标签式包装、工具说明语、无关读取元信息等噪音。

2. 落点收窄  
   让 citation 默认打开位置覆盖 citation 对应的核心 `snippet`，而不是宽泛附近区块。

3. 确认成本下降  
   让用户在打开后无需二次关键词搜索或明显滚动，即可理解证据点所在。

---

## 3. 非目标

- 不重新设计 citation 主链路
- 不改动 `precise/native` 与 `file/*` 的语义边界
- 不新增新的透明度组件
- 不为单个样本定制一次性补丁
- 不把 no-hit 场景纳入本阶段主优化范围

---

## 4. 实施策略

本阶段遵循以下实施顺序：

1. 先做分层诊断  
   按 A01、A03、A04、A05 逐一比对以下 3 个对象：
   - 原始 `source_refs.snippet`
   - 经过 `sanitizeCitationSnippet` 后的引用片段
   - preview 首屏实际展示与高亮范围

   该步骤的目标不是立即修改代码，而是识别问题到底属于：
   - 原生片段生成过脏
   - 适配层清洗不足或过弱
   - preview 加载窗口与高亮策略不够聚焦

2. 再确定最小修复落点  
   根据诊断结果，按以下优先级选择修复层级：
   - 原生层：当噪音直接来自 `read` 返回内容，且属于通用包装问题
   - 共享标准化层：当问题适合在 `sanitizeCitationSnippet` 一次性治理，并可同时改善引用面板与 tooltip
   - preview 层：当问题本质是首屏窗口大小、高亮命中策略或滚动定位不够聚焦

   只有在更低层无法通用解决时，才向更高层移动。

3. 最后做回归与人工走查  
   仅在 A01、A03、A04、A05 上验证本阶段效果，确认优化没有破坏 native 主路径，也没有引入新的显示副作用。

实施原则如下：

- 优先在最低且最通用的有效层级解决问题，不在更高层重复补偿
- 优先提升共享片段质量，不为单一题目手写特殊规则
- 优先保证首屏确认效率，不追求更复杂的展示形式
- 优先保留真实原文语义，不以过强清洗换取表面整洁

## 6. 工程验收口径

本阶段研发完成，至少满足以下条件：

1. A01、A03、A04、A05 的最终正文 citation 继续绑定 `precise/native`
2. citation 打开后的首屏默认证据片段不包含以下主要噪音：
   - `Assistant`
   - `User`
   - XML/标签式包装
   - 工具说明语
   - 与当前断言无关的读取元信息
3. 首屏可见区域覆盖 citation 对应的核心 `snippet`
4. 用户无需二次关键词搜索，且打开后首屏即可看到高亮证据片段，便可定位到支撑断言的片段
5. 未通过前端 fallback、正文反推 citation 或 synthetic/source path 冒充 native precise
6. 片段治理规则已被测试覆盖，且不会把真实原文中的正常内容误删为噪音

---

## 7. 风险与边界

- 若去噪规则过强，可能损伤真实原文内容，导致证据语义不完整
- 若落点裁剪过窄，可能损失理解当前断言所需的最小上下文
- 若实现位置选错，可能把原生证据优化重新做成应用层补偿
- 若仅凭现有 4 个样本调参，存在对局部样本过拟合的风险
- 若在共享标准化层过度清洗，可能破坏 preview 中基于 `snippet` 的高亮命中
- 若只改善引用面板文本而未同步改善 preview 首屏窗口，用户体感仍不会明显提升
- 若不同层各自引入局部规则，可能形成重复清洗与职责漂移

本阶段应优先选择：

- 可解释的通用规则
- 最小必要的上下文保留
- 能被后续 smoke 与人工走查持续验证的实现方式
- 单一主修复层与清晰职责边界

---

## 8. 维护方式

- 仅在目标、任务看板、工程验收口径发生变化时更新
- 新发现的噪音模式优先补入“通用去噪规则”范围，不单独扩展文档叙事
- 当验收流程独立发展为完整 checklist 或样本矩阵时，再拆分单独的 validation 文档
